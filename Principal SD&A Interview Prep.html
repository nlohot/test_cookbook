Q7How do you prioritise an automation backlog when every security team wants something?Architecture · Automation · Risk & controlPrincipal

Use a transparent scoring model and publish it:

Score = (Risk reduction × Frequency/Toil × Reuse potential × Confidence) ÷ (Effort × Operational risk)

  • Risk reduction: does it shorten exposure on crown-jewel assets, close an audit finding, or reduce a top risk-register item?
  • Toil: hours/month × number of people. Pull data from ServiceNow task volumes.
  • Reuse: does it build a component (e.g., CMDB owner lookup) others will use?
  • Operational risk: an automation that writes to production (disables accounts, isolates hosts) needs more engineering, so higher effort.

Then balance the portfolio: ~60% committed roadmap, ~20% platform/tech debt, ~20% quick wins/run. Review monthly with stakeholders; say no with data.

Q13Where are the trust boundaries in that architecture, and why do they matter?Architecture · Risk & control · ThreatPrincipal
  1. Untrusted content → model: alert fields, emails, filenames, code, scanner text and log lines are attacker-influenceable. Boundary control: Prompt Shields (document attacks), spotlighting, schema-validated context packs.
  2. Model → tools: the model's output is untrusted input to tools. Control: typed MCP tools that validate parameters and authorise each call; no free-form API or query passthrough for write operations.
  3. Agent identity → enterprise resources: control: managed identity or Agent ID per agent, least privilege, OBO when acting for a human, Conditional Access for workload identities.
  4. Agent ↔ agent (A2A / multi-agent): another agent's output is untrusted. Control: separate privileges (read-only researcher vs approval-gated actor), validate hand-offs.
  5. Platform → external SaaS/model endpoints: control: Private Link, APIM gateway, egress allow-list, data classification checks.
  6. Human approval channel: control: authenticated approvals (Entra-backed Teams card or ServiceNow), no self-approval, four-eyes for high risk.

from azure.ai.projects import AIProjectClient

project = AIProjectClient(
    endpoint="https://<foundry-resource>.services.ai.azure.com/api/projects/secauto",
    credential=DefaultAzureCredential())          # managed identity in Azure, az login locally

    "type": "mcp",
    "server_label": "secops_tools",
    "server_url": "https://apim.internal.example/mcp/secops",
    "allowed_tools": ["get_wiz_issue", "get_qualys_host_detections", "lookup_cmdb_owner"],
    "require_approval": "always",                 # human or orchestrator approves each call

    agent_name="vuln-triage",
    definition={
        "kind": "prompt",
        "model": "gpt-4.1-triage",                # deployment name in Foundry
        "instructions": open("prompts/vuln_triage_v3.md").read(),
        "tools": [mcp_tool],

resp = openai.responses.create(
    input="<task>Triage Wiz issue ISSUE-123</task>",

Q21Architecture: what is a Logic Apps agent workflow and how does the agent loop work?ArchitectureCore

An agent loop action uses an LLM in an iterative cycle: think (analyse inputs, choose an action), act (call a tool), optionally learn (adapt from feedback), keeping chat history up to the model's context limit.

  • Autonomous workflows start from any trigger (for example a Sentinel incident, a Service Bus message or a schedule) and return results to the caller. These are the security-automation workhorse.
  • Conversational workflows start with the When a chat session starts trigger and talk to a human through the chat interface (an analyst assistant).
  • Tools are containers of one or more connector actions; agent parameters are inputs that the model fills at run time.
  • Model source: Standard can use an Azure OpenAI resource, a Foundry project (preview; managed identity required) or APIM fronting an LLM API (preview, autonomous only). Consumption (preview) uses a Foundry-hosted model provisioned for you.
  • Multiple agents can run in sequence within one workflow; an agent can't be added inline as another agent's tool.
Q22Engineering: how do you design tools and agent parameters safely in a Logic Apps agent?EngineeringDeep dive
  • Keep it to about 10 tools or fewer per agent loop (Microsoft's guidance); name them precisely and write descriptions as contracts ("Returns the CMDB owner and support group for a hostname. Read-only.").
  • Decide which inputs the model may set. Fix sensitive values with dynamic content or expressions (e.g., the incident ID or subscription from the trigger) and let the model set only what it must. This is the main lever against excessive agency.
  • Use Compose actions to pass only the fields the model needs from tool results (data minimisation and lower tokens) and to mock side-effecting actions during design.
  • Separate read tools from write tools; put write tools behind an approval step outside the agent loop, or make the tool itself call a Durable Functions approval endpoint.
  • Write prescriptive instructions: role, allowed actions, prohibited actions, output format, what to do when uncertain.

def remediation_orchestrator(ctx):
    finding = ctx.get_input()
    context_pack = yield ctx.call_activity("BuildContextPack", finding)      # CMDB, Wiz, Qualys
    proposal = yield ctx.call_activity("AskTriageAgent", context_pack)      # Foundry agent, JSON out
    check = yield ctx.call_activity("ValidateProposal", proposal)           # schema, policy (OPA), blast radius
    if not check["ok"]:

    yield ctx.call_activity("RequestApproval", {"proposal": proposal, "id": ctx.instance_id})
    decision = yield ctx.wait_for_external_event("Approval")                 # plus a timer for timeout
    if decision["approved"]:
        result = yield ctx.call_activity("ExecutePlaybook", proposal["playbook"])  # pre-approved Ansible/ARM
        yield ctx.call_activity("VerifyAndClose", {"finding": finding, "result": result})

The agent never executes changes directly; it selects a pre-approved playbook and parameters that are validated before execution.

        retry = Retry(total=5, backoff_factor=1.5, status_forcelist=[429, 500, 502, 503, 504],
                      allowed_methods=["GET", "PUT", "DELETE"],   # POST only if idempotent
                      respect_retry_after_header=True)
        self.s.mount("https://", HTTPAdapter(max_retries=retry, pool_maxsize=20))

    def _request(self, method: str, path: str, **kw) -> requests.Response:
        headers = kw.pop("headers", {})
        headers["Authorization"] = f"Bearer {self._token_provider()}"
        resp = self.s.request(method, f"{self.base_url}{path}", headers=headers,
                              timeout=self.timeout, **kw)
        if resp.status_code == 401:                  # token expired mid-run -> refresh once
            headers["Authorization"] = f"Bearer {self._token_provider(force=True)}"
            resp = self.s.request(method, f"{self.base_url}{path}", headers=headers,
                                  timeout=self.timeout, **kw)
        if not resp.ok:
            raise ApiError(resp.status_code, resp.text, resp.headers.get("x-request-id"))
        log.info("api_call", extra={"method": method, "path": path,
                                    "status": resp.status_code,
                                    "ms": int(resp.elapsed.total_seconds() * 1000)})
        return resp

    def paginate(self, path: str, params: dict, items_key="result", page_size=500) -> Iterator[Any]:
        offset = 0
        while True:
            data = self._request("GET", path, params={**params, "limit": page_size,
                                                      "offset": offset}).json()
            items = data.get(items_key, [])
            yield from items
            if len(items) < page_size:
                break
            offset += page_size

Q62Explain idempotency and exactly-once in security workflows. How do you prevent duplicate tickets?Architecture · Engineering · Automation · Risk & controlDeep dive

True exactly-once delivery is rarely achievable; aim for at-least-once delivery + idempotent processing.

  • Idempotency key per business entity: e.g., sha256(source|finding_id|asset_key). Store it in ServiceNow (correlation_id / correlation_display) or a state table (Cosmos DB / Table Storage).
  • Upsert semantics: look up by correlation ID → update if exists, create if not. Use optimistic concurrency (ETags) when updating state.
  • Service Bus duplicate detection (MessageId-based within a time window) and sessions for ordered processing per asset.
  • Outbox pattern when you must write to your DB and emit an event atomically.
  • State transitions are monotonic: a finding closed by the scanner should not be reopened by a late-arriving older event; compare last_seen timestamps.

              "status": "New,Active,Re-Opened,Fixed",

Q124What is an AI agent, and what makes an agent workflow production-grade?Architecture · AutomationCore

Q130Explain RAG and the design decisions that matter for a security knowledge assistant.Architecture · Engineering · Risk & controlCore

RAG retrieves relevant documents at query time and feeds them to the LLM to ground answers.

Design decisions:

  • Corpus: security standards, runbooks, architecture docs, past incident reports, CIS benchmarks, vendor KBs. Curate; stale docs produce wrong answers.
  • Chunking: structure-aware (by heading/section), 300–800 tokens with overlap; keep metadata (doc, section, version, classification, owner).

  • Security trimming: document-level ACLs (Entra groups) enforced at query time so users only retrieve what they're allowed to see; this is non-negotiable in a bank.
  • Citations required in answers; "I don't know" when retrieval is weak.
  • Freshness: incremental indexing pipelines; versioned docs.

Rapid-fire technical round

Short questions with crisp answers for quick-fire panel segments.

Q178Rapid-fire: identity & protocolsCore
  • OAuth 2.0 vs OIDC? OAuth = authorisation (access tokens for APIs); OIDC = authentication layer on OAuth (ID token, user info).
  • Client credentials flow? Machine-to-machine; app authenticates with secret/cert/federated assertion, gets app-only token.
  • On-behalf-of flow? Middle-tier exchanges user's token for a downstream token preserving user identity, used for agents acting for analysts.
  • PKCE? Protects auth code flow from code interception; required for public clients and recommended for all.
  • SAML vs OIDC? SAML XML assertions, browser SSO, older enterprise apps; OIDC JSON/JWT, modern apps & APIs.
  • SCIM? Standard REST schema for user/group provisioning (Saviynt/Entra → SaaS).
  • JWT validation? Signature (JWKS), iss, aud, exp/nbf, algorithm allow-list (no none), scopes/roles.
  • CAE? Continuous Access Evaluation, near-real-time token revocation on critical events for CAE-aware resources.
Q179Rapid-fire: cloud & platformCore
  • Managed identity system vs user-assigned? System tied to resource lifecycle; user-assigned standalone, shareable, pre-provisionable.
  • Event Grid vs Service Bus vs Event Hubs? Event Grid = discrete event routing/push; Service Bus = enterprise messaging (queues/topics, ordering, DLQ, transactions); Event Hubs = high-throughput streaming/telemetry.
  • Azure Policy effects? Deny, Audit, Append, Modify, DeployIfNotExists, AuditIfNotExists, Disabled (+ DenyAction).
  • Private endpoint vs service endpoint? PE gives private IP in your VNet for a PaaS instance; SE extends VNet identity to the service's public endpoint.
  • AKS workload identity? K8s service account federated to Entra via OIDC issuer; pods get Entra tokens without secrets.
  • SCP vs IAM policy (AWS)? SCP sets max permissions for accounts in an Organization; doesn't grant; IAM policies grant within that boundary.
Q180Rapid-fire: vulnerability & AppSecCore
  • QID? Qualys vulnerability ID in its KnowledgeBase; maps to CVEs.
  • QDS vs TruRisk? QDS = detection-level score (1–100); TruRisk = asset/organisation risk incorporating asset criticality.
  • EPSS? Probability a CVE is exploited within 30 days.
  • KEV? CISA's Known Exploited Vulnerabilities catalogue.
  • SAST vs DAST vs SCA vs IAST? Static code; running app black-box; third-party dependencies; instrumented runtime analysis.
  • Security hotspot (Sonar)? Security-sensitive code requiring human review; not necessarily a vulnerability.
  • Reachability analysis? Determines whether vulnerable code in a dependency is actually invoked.
  • SBOM vs AI-BOM? SBOM lists software components; AI-BOM extends to models, datasets, embeddings, prompts, tools.
  • SLSA? Supply-chain Levels for Software Artifacts: build provenance integrity framework.
Q181Rapid-fire: AICore
  • Temperature? Randomness of sampling; 0 for deterministic-ish classification.
  • Context window vs RAG? Larger windows don't remove the need for retrieval (cost, latency, "lost in the middle," access control).
  • Embedding? Vector representation of text for semantic similarity.
  • Hybrid search? Keyword (BM25) + vector, fused (RRF) and reranked.
  • Function/tool calling? Model emits structured call (name + JSON args) that your code executes.
  • Jailbreak vs prompt injection? Jailbreak = user tries to bypass safety; injection = untrusted content hijacks instructions (often indirect).
  • LLM-as-judge risks? Bias, position/verbosity bias, self-preference; calibrate against human labels.
  • Hallucination mitigation? Grounding, citations, abstention, verification by tools, lower temperature, evals.
  • Agentic loop limits? Max iterations, token budget, timeouts, tool allow-lists.
Q182Rapid-fire: UNIX/Windows hardening (your domain)Core
  • auditd vs syslog? auditd = kernel-level audit events (syscalls, file watches, execve); syslog = general service/app logging.
  • SELinux modes? Enforcing, permissive, disabled; use targeted policy; never disable to "fix" an app.
  • sshd hardening essentials? PermitRootLogin no, PasswordAuthentication no, strong KEX/ciphers/MACs, AllowGroups, LogLevel VERBOSE, MaxAuthTries, idle timeouts, banner.
  • Kerberoasting? Requesting service tickets for SPN accounts and cracking offline; mitigate with gMSA/long random passwords, AES-only, monitoring 4769 anomalies.
  • LAPS? Unique, rotated local admin passwords stored in AD/Entra.
  • NTLM restriction / LDAP signing / channel binding? Mitigate relay attacks (you engineered these at Barclays).
  • Tiered admin model? Tier 0 (identity control plane), Tier 1 (servers), Tier 2 (workstations); no credential exposure downward.
